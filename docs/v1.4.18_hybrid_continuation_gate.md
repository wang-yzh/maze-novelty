# v1.4.18 Hybrid Continuation Gate

## Goal

`v1.4.17` recommended testing a middle gate between two extremes:

```text
signature consistency:
  structurally cleaner but too brittle

effect consistency:
  completes many more options but can become too permissive
```

This step implements and smokes:

```text
effect_structural_guard
```

The rule:

```text
continue while movement effect matches,
but abort if structural evidence does not arrive within a patience window
```

## Mechanism

The new continuation rule tracks:

- effect mismatch;
- structural evidence;
- structural aborts.

Current structural evidence is deliberately simple:

```text
goal visible
or the option produces real movement
```

The first implementation also tried a stricter evidence definition based on
larger displacement / region evidence. That was too harsh for short options and
collapsed completion on `N2-S4`, so the working implementation now treats real
movement as minimal structural evidence.

New config:

```text
structural_patience
```

The branch-specific preset now allows this value to be overridden from the CLI
with:

```bash
--reuse-structural-patience
```

New metrics:

- `target_reuse_first_step_structural_evidence_count`
- `target_reuse_structural_evidence_steps`
- `target_reuse_structural_abort_count`
- `target_reuse_structural_patience`

## Decision

Do not promote `effect_structural_guard`.

Keep it as an experimental rule and a useful negative result.

The result is still valuable because it confirms the shape of the tradeoff:

```text
strict structure gate:
  preserves some structural quality
  but kills too many options

effect-only gate:
  preserves completion
  but loses structural quality
```

The next refinement should not be "make the gate stricter or looser" globally.

It should be:

```text
structure requirement should depend on option kind
```

Examples:

- `forward_run` should require movement;
- `region_transition` should require region/subgoal evidence;
- `wall_follow` should tolerate turn-first behavior but require movement soon;
- `target_trace` should probably stay diagnostic only.

That is a narrower next step than another macro-cycle.
